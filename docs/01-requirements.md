# Требования к приложению «Последний рубеж»

**Версия:** 1.0 · **Дата:** 2026-11-10  
**Основа:** реализация MVP 0.6.0; это текущая спецификация, а не будущая гипотетическая SaaS-платформа.

## 1. О приложении

Многопользовательская игра «Последний рубеж» работает в браузере на компьютере. Ведущий создаёт комнату, участники заходят по коду и получают индивидуальные закрытые карты персонажей. Затем игроки в Discord обсуждают ситуацию, раскрывают карты и голосуют, кого исключить. Ведущий контролирует ход раундов. Зрители могут наблюдать, а администратор контента — вести паки характеристик.

**На начало работы:** реализованы все девять описанных ниже основных функций. Нуждаются в доработке/проверке: фиксация зависимостей, frontend E2E, сборка с чистого клона. Это не новые пользовательские функции.

**Термины:**
- **Комната** — игровая сессия с уникальным кодом, списком участников, ведущим и состоянием.
- **Пак** — версия набора характеристик, катастроф и параметров убежища; комната хранит снимок пака.
- **Персонаж/рука** — набор приватных карточек участника.
- **Раскрытие** — публикация выбранной карты остальным участникам комнаты.
- **Раунд** — стадия выступлений; **голосование** — отдельная фаза выбора кандидата на исключение.
- **Зритель** — пользователь с ограниченным доступом без карт/голоса.

## 2. Требования к функционалу

Приоритет: **обязательно** — в объёме семестра; **желательно** — можно улучшить; **потом** — за рамками. Состояние: **есть** — функция реализована в коде; **доработать** — реализована частично; **сделать** — отсутствует. Указанная реализация не означает, что все NFR проверены на чистой машине.

| ID | Формулировка | Приоритет | Состояние | Признак выполнения |
|---|---|---|---|---|
| **FR-1** | Ведущий может создать игровую комнату, выбрав пак, название и свой ник. | Обязательно | Есть | Появляется уникальный код комнаты и токен ведущего; начальное состояние `lobby`. |
| **FR-2** | Игрок может войти в доступную комнату по её коду, указав уникальный ник. | Обязательно | Есть | В лобби появляется участник, а после начала партии новый вход оформляется зрителем. |
| **FR-3** | Ведущий может начать партию после подключения минимум двух игроков. | Обязательно | Есть | Комната переходит в фазу `round`, активным игрокам выдаются индивидуальные руки. |
| **FR-4** | Игрок может просматривать свои закрытые карты и выборочно раскрывать их участникам комнаты. | Обязательно | Есть | Игрок видит `own_hand`, остальные получают только раскрытые значения. |
| **FR-5** | Активный игрок может отдать или изменить голос за кандидата либо за пропуск во время голосования. | Обязательно | Есть | Сервер сохраняет последний выбор и не раскрывает чужие голоса до подсчёта. |
| **FR-6** | Ведущий может переключать раунды, открывать и подводить итоги голосования. | Обязательно | Есть | При подсчёте происходит исключение, пропуск или второй тур по правилам игры. |
| **FR-7** | Зритель может наблюдать публичное состояние партии без доступа к чужим закрытым картам и управляющим действиям. | Обязательно | Есть | `spectator=true`, чужие закрытые карты не выдаются, команды запрещены. |
| **FR-8** | Администратор контента может создавать, редактировать и удалять пользовательские паки после проверки пароля. | Обязательно | Есть | Пак появляется/изменяется/удаляется в каталоге, неверный пароль отклоняется. |
| **FR-9** | Ведущий может отменить последнее поддерживаемое игровое действие либо завершить текущую партию. | Обязательно | Есть | При `undo` восстановлено предыдущее состояние; при `finish` фаза `finished`. |

### 2.1. Нефункциональные требования и ограничения

| ID | Проверяемое ограничение | Способ проверки | Статус подтверждения |
|---|---|---|---|
| **NFR-1** | Сервер не выдаёт участнику закрытые карты других игроков и чужие значения голосования через REST или WebSocket. | Интеграционные тесты `test_lobby_private_hand_reconnect_and_spectator`, `test_websocket_sync_never_pushes_private_cards`. | Тестами подтверждено локально |
| **NFR-2** | API изменения пака отклоняет неверный пароль администратора с кодом HTTP 403. | Запрос `POST /api/packs` c неправильным `X-Admin-Password`. | Реализовано; отдельная ручная проверка ещё нужна |
| **NFR-3** | Приложение должно запускаться из чистого клона на Docker Desktop с PostgreSQL 16 и отвечать на `/api/health` объектом `{"ok":true}` за не более чем 5 команд запуска после заполнения `.env`. | Чистый Docker Compose build, запрос health, запись ОС и даты. | Требует проверки |
| **NFR-4** | Комната принимает не более 30 активных игроков, а число незавершённых комнат ограничено `MAX_ROOMS` (по умолчанию 2). | API-верификация предельных значений и `test_room_cap_and_host_delete`. | Реализовано/частично покрыто тестами |
| **NFR-5** | После изменений игрового состояния соединённые участники получают по WebSocket уведомление `sync`; обновлённые данные они запрашивают персонально по HTTP. | Интеграционный WS-тест и просмотр сетевых сообщений двух клиентов. | Серверный WS-тест подтверждён; браузерный E2E не выполнен |

Текущее развёртывание предназначено **только для доверенной локальной/VPN-сети**, без публичного интернет-доступа. HTTPS и полноценная аутентификация не заявлены как существующие свойства.

## 3. Пользовательские сценарии

Общее правило: успешный ответ API для изменения комнаты возвращает статус 200, а конкретные случайные коды/токены **непредсказуемы**; в примерах указаны допустимые конкретные входы, проверяемые поля и точные сообщения об ошибках.

### US-1 — Создание комнаты (FR-1)

**Я как ведущий** имею доступ к странице и существующий пак `basic`, ввожу название и свой ник, выбираю пак, нажимаю «Создать комнату»; получаю код комнаты и токен ведущего, попадаю в лобби.

- **Вход:** `POST /api/rooms` с `{"title":"Вечер в бункере","nickname":"Командир","pack_id":"basic","config":{}}`.
- **Шаги:** 1) Открыть стартовую страницу. 2) Заполнить форму. 3) Создать комнату.
- **Выход:** HTTP 200, JSON с `id` (6 шестнадцатеричных символов в верхнем регистре), `token` и `player_id`; последующий `GET /api/rooms/{id}` с `X-Player-Token` содержит `phase="lobby"`, `me.host=true`.
- **Некорректный пример:** заменить `pack_id` на `missing`. Ожидается HTTP 404, `detail="Пак не найден"`; новая комната не создаётся.

### US-2 — Подключение игрока (FR-2)

**Я как игрок** имею код комнаты в фазе `lobby`, ввожу свободный ник, подключаюсь, получаю персональный токен и вижу участников.

- **Вход:** действительный `room_id`, `POST /api/rooms/{room_id}/join` с `{"nickname":"Алиса","spectator":false}`.
- **Шаги:** 1) Получить код у ведущего. 2) Ввести код и ник. 3) Подключиться.
- **Выход:** HTTP 200, `id`, `token`, `player_id`, `spectator=false`; участник отражён в состоянии комнаты.
- **Некорректный пример:** второй пользователь входит в ту же комнату с ником `Алиса`. Ожидается HTTP 400, `detail="Такой ник уже занят"`; второй участник не создаётся.
- **Альтернатива:** при входе после начала игры `spectator=true` независимо от запроса.

### US-3 — Старт игры (FR-3)

**Я как ведущий** имею комнату в лобби и минимум двух активных игроков, нажимаю «Начать»; получаю игровую фазу, стартовый сценарий и сгенерированные руки участников.

- **Вход:** действительный токен ведущего, команда `{"type":"start","data":{}}`.
- **Шаги:** 1) Дождаться второго участника. 2) Начать партию. 3) Посмотреть свой набор.
- **Выход:** фаза `round`, у ведущего непустой `own_hand`; чужие руки закрыты.
- **Ошибка:** при одном игроке HTTP 400 `Для старта нужно хотя бы 2 игрока`; фаза остаётся `lobby`.

### US-4 — Раскрытие карт (FR-4)

**Я как игрок** имею личный токен и хотя бы одну закрытую карту, выбираю её и раскрываю; получаю опубликованное значение карты в общей таблице.

- **Вход:** авторизованный `GET /api/rooms/{id}` и `POST .../command` с `{"type":"reveal","data":{"card_id":"<id моей карты>"}}`.
- **Шаги:** 1) Открыть свою руку. 2) Выбрать карту. 3) Подтвердить раскрытие.
- **Выход:** `players[].revealed` содержит раскрытую карту у всех пользователей; остальные закрытые значения видны только владельцу.
- **Ошибка:** чужой `card_id` отклоняется без раскрытия его значения.

### US-5 — Голосование (FR-5)

**Я как активный игрок** имею игровую комнату в фазе `voting`, выбираю другого активного игрока или `skip`, отправляю голос и могу изменить выбор до подсчёта.

- **Вход:** после `{"type":"open_vote","data":{}}` от ведущего: `POST /api/rooms/{id}/vote` с `{"target":"skip"}` и заголовком `X-Player-Token: <мой токен>`.
- **Шаги:** 1) Дождаться открытия голосования. 2) Выбрать «Пропустить». 3) Отправить голос. 4) При необходимости изменить выбор.
- **Выход:** HTTP 200 `{"ok":true}`, в моём состоянии `state.my_vote="skip"`, увеличивается `vote_count`; другим виден статус участия, но не мой выбор.
- **Некорректный пример:** отправить тот же запрос в фазе `round` до открытия голосования. Ожидается HTTP 400, `detail="Голосовать сейчас нельзя"`; голос не сохраняется.

### US-6 — Управление раундом (FR-6)

**Я как ведущий** имею комнату с активной партией, открываю голосование, затем подсчитываю голоса и перехожу к следующему раунду; вижу результат подсчёта и актуальный список активных участников.

- **Вход:** токен ведущего, команды `open_vote`, `resolve_vote`, `next_round`.
- **Выход:** `voting`/`round`, `vote_result`, обновлённый `alive` у исключённых или второй тур.
- **Ошибка:** `resolve_vote` до открытия голосования → ошибка `Сейчас нет голосования`.

### US-7 — Просмотр зрителем (FR-7)

**Я как зритель** имею код комнаты, присоединяюсь в режиме наблюдения, вижу раскрытые карты, сценарий и события, но не получаю руку и не могу голосовать.

- **Вход:** `{"nickname":"Наблюдатель","spectator":true}` на endpoint присоединения.
- **Выход:** `spectator=true`, `own_hand=[]`, только открытые характеристики других игроков.
- **Ошибка:** команда `start` от зрителя → HTTP 403 `Зрители не могут управлять игрой`.

### US-8 — Редактирование паков (FR-8)

**Я как администратор контента** знаю серверный пароль, создаю новый пак на основе структуры JSON и сохраняю его для будущих комнат.

- **Вход:** `X-Admin-Password`, JSON `{"content":{...}}` с категориями, катастрофами и параметрами бункера.
- **Выход:** новый `id` и `revision=1`; пак в `GET /api/packs`.
- **Ошибка:** неверный пароль → HTTP 403 `Неверный пароль администратора`; новый пак не создаётся.

### US-9 — Откат/завершение (FR-9)

**Я как ведущий** управляю активной партией и могу отменить последнее действие или завершить игру, чтобы зафиксировать её результат.

- **Вход:** токен ведущего, команда `undo` или `finish`.
- **Выход:** восстановление предыдущего состояния или `phase="finished"`.
- **Ошибка:** команды ведущего от обычного игрока отклоняются HTTP 403.

**О соответствии модели данных коду:** `Pack`, `Room`, `Player` — таблицы SQLAlchemy; `Card` и `Vote` — **логические** сущности, хранящиеся в JSON-полях (`Player.hand` и `Room.state.votes`), отдельные таблицы для них в текущей реализации отсутствуют.

**Состояния:** `lobby` (набор игроков), `round` (обсуждение/раскрытие), `voting` (голосование), `finished` (результат). После завершения возможны публичные раскрытия, но не продолжение обычной игровой логики. Автоматическое завершение при заполнении убежища зависит от числа оставшихся активных участников.

## 5. Валидация документа

- Согласование требований и диаграмм: внутреннее, без подтверждения преподавателя.
- Peer-review: ожидается от участника команды или назначенного студента; комментарии/approve/resolve и PR в GitHub оформляются **только фактическими действиями**.
- Известная граница качества: Docker/браузер на независимой машине и performance NFR не тестировались в этой сессии.
