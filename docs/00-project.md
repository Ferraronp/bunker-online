# Паспорт проекта — «Последний рубеж»

**Версия паспорта:** 1.0 (2026-11-10)  
**Тип проекта:** собственный проект; учебная копия существующего исходного кода, не форк стороннего репозитория.  
**Исходная база:** предоставленный архив `bunker-project-v6.zip` (исходная версия приложения 0.6.0, 2026-10-30).  
**Состояние:** играбельный MVP для доверенной компании друзей; не production SaaS.

## 1. Назначение и проблема

«Последний рубеж» — многопользовательское desktop-first веб-приложение для проведения игры о выборе выживших в убежище. Участники разговаривают в Discord, но на сайте создают комнату, получают приватные характеристики персонажа, раскрывают их, голосуют и видят результаты. Система заменяет ручную раздачу карточек, подсчёт голосов и фиксацию состояний партии. Регистрация аккаунтов и встроенный голосовой чат **не входят** в текущую версию.

## 2. Пользователи и роли

| Роль | Возможности |
|---|---|
| **Ведущий** | Создать комнату, участвовать как игрок, запускать партию, управлять раундами, голосованием, откатом и завершением |
| **Игрок** | Присоединяться до старта, видеть свою руку, раскрывать карты, голосовать |
| **Зритель** | Подключиться для наблюдения, видеть только публичные сведения; не голосовать и не управлять игрой |
| **Администратор контента** | По серверному паролю создавать, изменять и удалять пользовательские паки |

Ведущий и игрок имеют отдельные уровни полномочий; администратор паков не обязательно является ведущим комнаты.

## 3. Три ключевые функции

1. Создание комнаты и присоединение игроков по коду/ссылке.
2. Раздача приватных характеристик, выборочное раскрытие, синхронизация состояния участников.
3. Проведение голосований, обработка ничьей, исключение игроков и завершение партии.

Полная карта из девяти функций приведена ниже; формальные требования FR-1…FR-9 находятся в [01-requirements.md](01-requirements.md).

## 4. Стек и лицензия

- Frontend: React 19, TypeScript, Vite 6, CSS, nginx.
- Backend: Python 3.12 (задан в CI), FastAPI, Pydantic, SQLAlchemy, Alembic.
- Хранение: PostgreSQL 16 в Docker Compose; SQLite для локальной разработки/тестов.
- Обновления в реальном времени: WebSocket для уведомления `sync` плюс приватизированный REST-запрос.
- Инфраструктура: Docker Compose, GitHub Actions; локальная или VPN-сеть.
- Лицензия учебной копии: **MIT** (файл `LICENSE`); до публичного размещения владелец исходников подтверждает выбор лицензии.

## 5. Команда и распределение

Состав учебной команды **не подтверждён**. Для индивидуального выполнения предусмотрены роли: владелец продукта/разработчик — владелец репозитория; разработка и тестирование — тот же участник. Ревью выполняет назначенный преподавателем студент другой команды. Если работа командная, имена, роли и трудозатраты следует вписать перед сдачей. Нельзя подменять фактическое peer-review автоматическими комментариями.

## 6. Структура и точки входа

| Путь | Назначение |
|---|---|
| `frontend/src/main.tsx` | React-интерфейс: лобби, партия, карточки, редактор паков |
| `frontend/src/style.css` | UI desktop-first |
| `frontend/vite.config.ts` | dev-server и проксирование REST/WebSocket |
| `backend/app/main.py` | FastAPI endpoints и WebSocket `/ws/rooms/{room_id}` |
| `backend/app/game.py` | Правила партии, голосование, раскрытия, откат, приватные DTO |
| `backend/app/db.py` | SQLAlchemy-модели `Pack`, `Room`, `Player`, подключение БД |
| `backend/app/seed.py` | Базовый игровой пак и генерация контента |
| `backend/migrations/` | Миграция Alembic |
| `backend/tests/test_api.py` | Интеграционные тесты API и игровых правил |
| `docker-compose.yml` | PostgreSQL + API + nginx/SPA, порты и тома |
| `.github/workflows/ci.yml` | CI с Pytest и сборкой frontend |

**Внешние системы:** браузер участника и его WebSocket; Docker; PostgreSQL. Discord — внешний канал голосового общения **без программной интеграции**. Внешних LLM/API для основных функций не нужно.

**Хранение и конфигурация:** таблицы `packs`, `rooms`, `players`; JSON-поля `Room.state`, `Room.pack_snapshot`, `Room.undo_stack`, `Player.hand`. Конфигурация через `.env` (`POSTGRES_PASSWORD`, `ADMIN_PASSWORD`, `PORT`, `MAX_ROOMS`) и параметры комнаты. Секреты не коммитятся.

## 7. Карта пользовательских функций (состояние на исходном архиве)

| Функция / ID | Реализация | Ручная проверка | Статус |
|---|---|---|---|
| FR-1 Создать комнату | `backend/app/main.py:create_room`, frontend | Создать комнату с ником и паком | Есть |
| FR-2 Присоединиться | `main.py:join_room` | В другом браузере войти по коду | Есть |
| FR-3 Запустить партию | `game.py:start`, `action` | Ведущий начинает после входа двух игроков | Есть |

| FR-5 Голосовать | `main.py:vote`, `game.py:cast_vote` | Изменить голос до подсчёта | Есть |
| FR-6 Управлять раундами и итогом | `game.py:action` (`open_vote`,`resolve_vote`,`next_round`) | Ведущий считает голоса и начинает следующий раунд | Есть |
| FR-7 Наблюдать | `main.py:join_room`, `game.py:public_state` | Войти зрителем, проверить запрет управляющих команд | Есть |

## 9. Наблюдения и issues

Требование задания — оформить **не менее трёх настоящих GitHub issues**. Для создания подготовлены [черновики](issues/README.md). После публикации заменить пометки ниже прямыми ссылками на созданные issues.

1. **BUG-1:** нет проверенного lock-файла и воспроизводимого полного dependency graph для frontend и backend.
2. **QUESTION-1:** `frontend/src/main.tsx` и `backend/app/game.py` монолитны; нужен план выделения модулей и регрессионных тестов.
3. **QUESTION-2:** нужны фронтенд unit/e2e проверки ключевых пользовательских сценариев и проверка браузерной совместимости.

## 10. Проверка запуска (протокол)

**Повторяемый сценарий для Windows + Docker Desktop:**

1. Скопировать `.env.example` в `.env`, задать собственные сильные `ADMIN_PASSWORD` и `POSTGRES_PASSWORD`.
2. Выполнить `docker compose up -d --build` и открыть `http://localhost:8080/api/health` — ожидается `{"ok":true}`.
3. Создать комнату, подключиться вторым браузером, запустить партию и раскрыть одну карту; проверить синхронизацию.

**Фактически проверено:** 2026-11-10, Linux/Python 3.13.5, `cd backend && PYTHONPATH=. pytest -q` → `26 passed`.  
**Не проверено:** Windows/Docker Desktop с чистого клона; полный фронтенд build и ручной E2E; дата/ОС/проверяющий на независимой машине. Эти данные нужно вписать после реального прогона, не выдумывая протокол.

## 11. Исследование выполнимости

| Риск | Тип | Вероятность | Последствия | Снижение |
|---|---|---|---|---|
| Нет lock-файлов, зависимости меняются | технический | Средняя | Сборка перестанет повторяться | Создать lock-файлы, проверять `npm ci` и Docker build в CI |
| Монолитные игровые модули | технический | Высокая | Трудность доработок и ревью | Выделить сценарии, обработчики, UI-компоненты, покрыть тестами |
| Разные браузеры и обрывы WebSocket | технический | Средняя | Десинхронизация комнаты | Сценарии reconnect, интеграционный/E2E тест |
| Нехватка времени/рецензента | организационный | Средняя | Задержка PR и документации | Ограничить учебный scope, назначить ревью заранее |
| Развёртывание через Radmin/локальную сеть | внешний | Средняя | Игроки не смогут подключиться | Инструкция по портам/файрволу, альтернативный локальный тест |
| HTTP/пароли в доверенной сети | безопасность | Высокая при публикации наружу | Перехват токенов и управление игрой | Не выставлять в интернет без HTTPS и полноценной аутентификации |
| Правовая неопределённость игровых названий/материалов | внешний | Низкая–средняя | Претензии к контенту | Использовать оригинальные тексты; сверить лицензию перед публикацией |
